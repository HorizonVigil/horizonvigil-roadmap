**Method:** static inventory generated from source, cross-checked against live

## VERDICT

**NOT PRODUCTION READY.** One confirmed data-destruction path, live in
production at the time of audit.

> **RESOLUTION, same day.** Finding 1 is **CLOSED**. A shared page walker
> (`pagination.ts`) and a universal truncation guard
> (`reportTruncationIfUnread` in `awsApi.ts`) now report a *successful but
> incomplete* response as degraded coverage — at the one chokepoint every
> scanner threads through, so all ~150 inherit it without being individually
> rewritten. Finalize refuses to tombstone a degraded type, which is what
> closes the path. EC2, ACM, SNS, SQS and IAM are migrated onto the walker.
> Findings 3 and 5 are partly addressed. Findings 2 and 4 remain open.
> See [the resolution section](#resolution-2026-09-15) at the end.

The connector is far better engineered than a NO-GO verdict suggests —
credentials, retry, throttling, error normalization, tenant isolation, durable
jobs and generation-safe tombstoning are all real and centralized. The failure
is narrow and severe: **it has no concept of an incomplete read.**

## FINDING 1 — CRITICAL: 88 scanners are structurally capped at one page

### Measured

| measure | value |
|---|---|
| scanner files | 111 |
| contain **any** pagination token handling | **19** |
| contain none | 92 |
| …of those, make real AWS calls | **88** |
| …of those, contain any `while`/`do` loop | **0** |
| pagination helper in shared layer (`HEAD`) | **none exists** |

`callQueryApi` and `callJsonApi` each issue exactly **one** HTTP request. They
handle signing, timeout, retry, backoff and error normalization correctly —
and then return a single response body. There is no pagination helper in
`HEAD` at all.

So 88 scanners do not fail to paginate. **They cannot paginate.**

### This is not theoretical — it is live

`ssm.ts` sets `MaxResults: 50` on seven operations and contains **zero**
pagination tokens (verified: `grep -c` returns 0).

Production, `kamal-k8s`:

```
systems_manager_inventory = exactly 50 rows
```

Exactly the page size. The scanner is discarding everything past the first
page right now, and reporting success.

### Why it destroys data rather than merely under-reporting

`computeFinalizeResult` tombstones a resource when:

```
r.last_seen_at < runStartedAt
  && coveredResourceTypes.includes(r.resource_type_key)
  && !degraded.has(r.resource_type_key)
  && <scope proven>
```

A truncated read **succeeds**. So its type is "covered", it is not "degraded",
and its scope is "proven". Every resource past page 1 therefore satisfies all
four conditions and is marked `DELETED`.

This is exactly the catastrophe the brief names:

> AWS API failure → empty response → "resource does not exist" → resource deleted

except it is worse, because there is no failure to detect. It is a
*successful* truncated read.

It has not fired destructively yet only because this estate is small enough
that most scanners fit in one page. **On the first scan of an enterprise
account it would tombstone real infrastructure.**

### Root cause

The system models two outcomes — SUCCESS and FAILURE — and correctly refuses
to tombstone on FAILURE (`degradedResourceTypes`). It has **no third state for
a successful but incomplete read.** Phase 5's `PARTIAL_SUCCESS` genuinely does
not exist.

## WORKING-TREE HAZARD

The `horizonvigil-connector-aws` working tree **does not compile** and is
being modified by a process other than this session:

| file | state |
|---|---|
| `src/lib/pagination.ts` | untracked, **corrupted** — re-exports `detectQueryTruncation`/`detectJsonTruncation` from `./paginationSignals` at line 44 *and* re-declares them at 89/112/144 |

| `src/lib/awsErrors.ts` | modified, uncommitted |

This matters operationally: `gcloud builds submit .` uploads the **working
tree**, not the committed tree. Deploys therefore ship uncommitted work. That
mechanism already shipped 829 lines of `ec2.ts` and 629 of `iam.ts` scan
diagnostics that were absent from git (now committed, PR #29).

**Deploys must be made from `git archive HEAD`, not from the working tree.**

## RESOLUTION 2026-09-15

Same day, verified against production.

### Finding 1 — CLOSED

| change | effect |
|---|---|
| `pagination.ts` + `paginationSignals.ts` | a real page walker with a typed `PaginationTermination` (`complete` / `page_cap` / `repeated_token` / `failed` / `malformed`) |
| `reportTruncationIfUnread` in `awsApi.ts` | reports a **successful but incomplete** response as degraded coverage, at the one chokepoint all ~150 scanners share |
| `incompleteSink` | routes an incomplete walk into the same sink AWS failures already use |
| EC2 · ACM · SNS · SQS · IAM migrated | 38 operations now walk pages instead of reading one |

The guard is what makes this universal. A scanner that has not been migrated
still cannot silently truncate, because the guard fires on the response rather
than inside the scanner. Correctly-paginating walkers suppress it
(`pagination: 'follow'`) so a page-1 response is not reported as degraded on
every call.

**`PARTIAL_SUCCESS` now exists.** Operation telemetry records `partial` when a
walk terminates incomplete, and `not_supported` for a retired or un-enabled
capability — so a healthy scan of an account that does not use a service stops
being reported as failing.

### A production failure found and fixed while verifying

EC2 collection was failing in **all 17 regions** of `kamal-k8s`. AWS retired
Elastic Graphics; `DescribeElasticGpus` began answering
`UNSUPPORTED_CAPABILITY`; and the call helper threw after exhausting its own
retries, so the rejection propagated out of the `Promise.all` that fans out
every EC2 Describe — discarding the thirty-three calls that had succeeded.

`iam.ts` carried the identical defect and had not been reached. IAM is a
**global** scanner, so there is no per-region blast radius: one failed `List*`
would have lost the entire account's IAM inventory.

Both now record the operation and continue. IAM keeps one deliberate throw:
if `ListUsers` is **denied**, returning empty would publish "0 IAM users" for
an account whose IAM we were simply not permitted to read.

### Finding 5 — partly closed

EC2 and IAM both carried hand-rolled retry loops duplicating `withRetry`
inside `callQueryApi`. Two layers meant up to 4 x 4 = **16 attempts** against a
throttled endpoint — making throttling worse, not better. Both removed; retry
lives in one place. One scanner still bypasses the shared client.

### Finding 3 — partly closed

Per-scanner tests went from **1** to **3** (`ec2`, `iam` failure semantics,
plus the shared `pagination` and `truncationGuard` suites). Still far short of
Phase 27's matrix.
